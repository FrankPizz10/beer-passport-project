# db/: PostgreSQL schema and catalog import

This directory holds the scripted catalog import that turns the cleaned catalog baseline into a loaded PostgreSQL database (Milestone 1, step 2). The database schema itself lives where it belongs: `prisma/schema.prisma` in `beer-passport-server` (PostgreSQL port merged via that repo's release/2.0 branch), with its baseline migration in that repo's `prisma/migrations/`.

## Contents

- The schema and DDL: `beer-passport-server`, `prisma/schema.prisma` and `prisma/migrations/20261027000001_init/migration.sql` (generated by Prisma 6.19.3, plus one hand-added CHECK constraint, audit F-1). Audit fixes applied in the port are listed in the schema header and in decisions/002.
- `src/catalog_import.py`: reads the catalog baseline from `experiments/catalog-discovery/data/` and writes PostgreSQL COPY files, an idempotent `load.psql`, and `import_manifest.json` into `output/` (gitignored). Validation fails the run before anything is written: frozen row counts (beers 5,894; breweries 1,339; categories 14; styles 147), unique ids, referential integrity, and value formats, including rejecting sentinel or implausibly short UPCs.
- `tests/`: unit tests for the transforms and validation, with small fixtures.

## Loading a database (what Milestone 1 step 5 runs on the box)

```sh
cd db
python -m src.catalog_import            # writes output/
psql "$DATABASE_URL" -f <beer-passport-server>/prisma/migrations/20261027000001_init/migration.sql
cd output && psql "$DATABASE_URL" -f load.psql
```

`load.psql` is an **initial load only** script: it refuses to run if any user or enrichment rows exist (guard at the top), because it truncates the catalog tables. It loads in foreign-key order and resets each id sequence to MAX(id), so preserved source IDs and future inserts coexist correctly. User tables from the EFS recovery load after the catalog, in step 5's own scripts.

## Verified by the step 2 load proof (2026-10-27)

Against PostgreSQL 16.2: DDL applied; load committed with exact counts (14 / 147 / 1,339 / 5,894); 27 discontinued rows; all UPCs NULL (the old catalog never had real barcodes); max ids preserved (beers 6,055, breweries 1,442) with the next insert taking 6,056; the F-1 check rejects a reversed friend pair; the F-5 Restrict constraint blocks deleting a beer a user has logged; deleting a user cascades their user_beers and friends; the initial-load guard fires when user data is present.

## Deferred to the Milestone 3 schema pass

From the schema audit (research/db-schema-audit.md): F-3 notifications uniqueness redesign, F-6 want-to-try state in user_beers, F-8 breweries_geocode resolution (real FK or drop), F-12 multi-device push tokens. F-10 (brewery-less duplicate beers) is handled by import validation for now: every baseline beer carries a brewery_id.

## Environment note

`prisma validate` passes on this schema (Prisma 6.19.3). In sandboxed environments where the Prisma engine CDN is unreachable, the CLI fails silently at install; fetch `schema-engine` and `libquery_engine` for the `@prisma/engines-version` commit from binaries.prisma.sh and set `PRISMA_SCHEMA_ENGINE_BINARY` / `PRISMA_QUERY_ENGINE_LIBRARY`.
