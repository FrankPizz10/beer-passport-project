**Status meanings (from the audit):** Observed in code = visible directly in the source reviewed. Needs verification = strong concern from code structure; confirm with tests or deployed configuration. Design recommendation = a change recommended for the relaunch, not necessarily a current defect.

## 1. Backend and deployment

### 1.1 Environment file copied into the Docker image (High, Observed in code)

- **Repo/component:** `beer-passport-server`, `Dockerfile`.
- **Evidence:** The Dockerfile explicitly copies `.env` into the image build context. The repository ignores `.env`, but the file may still be present on a developer or CI machine.
- **Impact:** Secrets or environment-specific values can be baked into image layers.
- **Remediation:** Remove the build-time `.env` copy; add/verify a `.dockerignore` excluding `.env`, local secrets, dependency folders, and build artifacts; inject configuration at runtime; keep secrets in AWS Secrets Manager or the hosting provider's secret store.
- **Hub note:** a `.dockerignore` now exists in the repository (26 bytes); its contents have not been verified to exclude `.env`.

### 1.2 Runtime secret loader writes a `.env` file (Medium-High, Observed in code)

- **Repo/component:** `beer-passport-server`, `src/Environment/environmentVariablesClient.ts`.
- **Evidence:** Reads the backend secret from AWS Secrets Manager and writes the values to a local `.env` file; includes MySQL-specific settings such as `MYSQL_ROOT_PASSWORD` and `MYSQL_DATABASE`.
- **Impact:** Secrets written to disk; settings reflect the old deployment model.
- **Remediation:** Return validated configuration and assign it directly to process configuration instead of writing secrets to disk; remove MySQL-container-only settings if the database becomes a separate managed service; confirm the runtime IAM role has only the Secrets Manager permissions it needs.

### 1.3 Database lifecycle is coupled too closely to the API (Critical, Known architectural problem)

- **Repo/component:** `beer-passport-server` deployment design.
- **Evidence:** The existing setup has run MySQL alongside the backend service/container.
- **Impact:** Scaling or replacing API containers can create competing database instances or risk data persistence, depending on volumes and orchestration.
- **Remediation:** Move database storage and lifecycle outside API containers; use a managed relational database or another clearly persistent single database service; document backups, restore steps, connection limits, and rollback before migrating production data; compare total monthly cost rather than assuming serverless is cheapest.

### 1.4 Catalog seeding/import happens during API startup (High, Observed in code)

- **Repo/component:** `beer-passport-server`, `src/DBclient/seedDatabase.ts`, invoked from startup.
- **Evidence:** The backend invokes `seedDatabase()` during startup; the seed logic checks whether tables are empty and, outside production, can retrieve catalog data from the production API; the production path of that helper returns an empty object.
- **Impact:** Data initialization and application startup are unnecessarily interdependent; confusing when bootstrapping new environments.
- **Remediation:** Move seeding and catalog imports into explicit scripts or admin jobs; make import scripts repeatable and safe to rerun with validation, duplicate detection, and an import report; use Prisma migrations for schema changes; document intended behavior for empty databases in development, test, staging, and production.

### 1.5 Error middleware placement may miss route errors (High, Needs verification)

- **Repo/component:** `beer-passport-server`, backend entry point.
- **Evidence:** The Sentry/error-handling middleware appears before the route registrations; in Express, error middleware generally needs to be registered after the routes whose errors it should catch.
- **Impact:** Errors from route handlers may not be captured by the centralized handler or reach Sentry.
- **Remediation:** Move centralized error middleware after route registration following the supported Sentry SDK setup; test sync errors and rejected async handlers; ensure errors produce safe client responses while retaining diagnostics in logs/monitoring.

### 1.6 Authentication failure status codes are inconsistent (High, Observed in code)

- **Repo/component:** `beer-passport-server`, `src/Middleware/authUsers.ts`.
- **Evidence:** Some authentication failure paths return JSON without explicitly setting an HTTP error status; Express defaults to 200.
- **Impact:** Failed authentication can look successful to clients even when the body describes an error.
- **Remediation:** Return 401 for missing/invalid authentication and 403 for authenticated users lacking permission; use a consistent documented error response shape; add API tests for missing, expired, invalid, and valid Firebase ID tokens, plus non-admin access to admin routes.

### 1.7 Prisma CLI and client versions differ (Medium, Observed in package configuration)

- **Repo/component:** `beer-passport-server`, `package.json`.
- **Evidence:** `@prisma/client` 4.14.0 vs Prisma CLI 4.11.0.
- **Impact:** Confusing generation or migration behavior, especially during a provider migration.
- **Remediation:** Align `prisma` and `@prisma/client` versions; pin Node/runtime and package-manager versions and commit the lockfile; test schema generation and migrations against a fresh database in CI.

## 2. Database and data model

### 2.1 MySQL-to-PostgreSQL migration decision is unresolved (High before relaunch, Design decision)

- **Repo/component:** `beer-passport-server`, Prisma schema.
- **Evidence:** Schema is Prisma-based, so the provider can change; but it is not a one-line edit (native types, indexes, constraints, migrations, SQL assumptions, data conversion).
- **Impact:** Decision gates the relaunch; doing it later is more disruptive.
- **Remediation:** Back up MySQL and record row counts; create a PostgreSQL test database, migrate schema and data preserving IDs and relationships; compare row counts, foreign keys, user histories, collection progress, badges, notifications; run integration tests before cutover with a tested rollback plan; compare real monthly costs of managed options.

### 2.2 Friend relationships may be stored twice (Medium, Observed schema concern)

- **Repo/component:** `beer-passport-server`, Prisma schema.
- **Evidence:** Uniqueness constraint is on `(user_1, user_2)`; does not prevent a second row with the IDs reversed.
- **Impact:** Duplicate/reversed friendship rows, depending on application logic and existing data.
- **Remediation:** Define whether friendships are directional or mutual; if mutual, enforce one canonical pair; add tests for repeated requests, reverse-direction requests, self-friending, and removal.

### 2.3 Barcode/UPC representation may lose leading zeros (Medium, Observed schema concern)

- **Repo/component:** `beer-passport-server`, Prisma schema.
- **Evidence:** The `upc` field is an integer; barcodes are identifiers, and integer storage can discard leading zeros or be unsuitable for longer formats.
- **Impact:** Data corruption for barcodes with leading zeros.
- **Remediation:** Evaluate storing barcodes as strings; inspect existing values, import sources, and uniqueness requirements first; add normalization and duplicate checks to catalog imports.

### 2.4 Notification uniqueness can collapse repeated events (Medium, Observed design trade-off)

- **Repo/component:** `beer-passport-server`, notifications.
- **Evidence:** Notifications use a unique key involving `(user_id, message)`; some handlers upsert by that key, so repeated events with the same message update an existing row rather than creating a distinct event.
- **Impact:** Repeated events may not be recorded as event history (may be intentional for some types).
- **Remediation:** Decide which notification types deduplicate vs record separately; prefer stable event identifiers or event-specific uniqueness rules; test repeated badge awards and friend events.

### 2.5 Catalog and history endpoints need deliberate query limits (Medium-High, Needs endpoint-by-endpoint verification)

- **Repo/component:** `beer-passport-server` routes; `beer-passport` client.
- **Evidence:** The mobile client requests basic catalog lists and the backend exposes catalog routes; unbounded list responses not yet ruled out.
- **Impact:** Large responses, slow search, excessive data transfer.
- **Remediation:** Server-side search, pagination, sort, filters; explicit response fields; indexes based on measured query patterns; latency tests against the full catalog.

## 3. Authentication, authorization, and privacy

### 3.1 Protect user-specific data at the API layer (High, Needs broader endpoint review)

- **Repo/component:** `beer-passport-server`, user-beer and badge routes.
- **Evidence:** `res.locals.user` pattern is good and Firebase ID tokens are verified, but some routes accept another user's numeric ID; a `private` profile field exists, so privacy rules must be enforced consistently by the backend.
- **Impact:** Potential unauthorized access to other users' data.
- **Remediation:** Audit every endpoint accepting a user ID; classify as self-only, public-profile, friend-only, or admin-only; enforce privacy and friendship checks server-side; avoid returning unnecessary personal fields; test private profiles, non-friends, friends, and unauthenticated callers.

### 3.2 Admin claim checks are present, but should be tested end-to-end (High, Positive foundation; verification recommended)

- **Repo/component:** `beer-passport-admin` (`src/MainScreen/SignInPage.tsx`), `beer-passport-server` (admin-token middleware).
- **Evidence:** Admin sign-in page checks the Firebase ID token's `admin` claim; backend includes admin-token middleware. Client-side check is UX only; server-side authorization is the boundary.
- **Impact:** Unverified server-side coverage on every admin route.
- **Remediation:** Verify every administrative API route uses server-side authorization; test non-admin users calling endpoints directly; keep Firebase custom-claim assignment restricted to trusted Cloud Functions/service credentials; add tests for claim revocation/refresh and expired tokens.

## 4. Mobile app and link website

### 4.1 Apple association route renders HTML rather than a raw association file (High for sharing, Observed in route implementation)

- **Repo/component:** `beer-passport-web`, `src/pages/rewritter.tsx`.
- **Evidence:** Renders the Apple App Site Association JSON inside a `<pre>` element; Universal Links require the file served as JSON at the expected URL, not as an HTML page.
- **Impact:** Universal Links may fail Apple's association-file requirements.
- **Remediation:** Serve the association file as a static asset or raw JSON response at the exact expected path; verify content type, status, body, HTTPS delivery, and domain configuration; confirm deployed domain and app identifier match the mobile app's associated-domain configuration.

### 4.2 Link path and deep-link parsing may disagree (High, Observed code mismatch; runtime behavior needs testing)

- **Repo/component:** `beer-passport` (`Controllers/DeepLinkContext.tsx`, navigation config).
- **Evidence:** Navigation expects `/beers/:id`; the custom handler parses a query parameter named `id` and maps the path to a screen name; the handler only processes a link when a user is present.
- **Impact:** Shared URLs may not resolve consistently; unauthenticated link-opening behavior is undefined.
- **Remediation:** Choose one canonical URL format per beverage; support opening a link before sign-in, preserving the destination until authentication completes; test cold start, app running, signed-in, signed-out, installed, and not-installed scenarios; verify Android App Links separately.

### 4.3 Share links need a useful web fallback (High, Relaunch requirement)

- **Repo/component:** `beer-passport-web`.
- **Evidence:** A shared beverage link currently can dead-end when the app is missing.
- **Impact:** Broken sharing experience; lost acquisition.
- **Remediation:** Stable canonical URL per beverage; useful indexable web landing page with beverage name, brewery, approved image or fallback artwork, and App Store/Play Store links; graceful handling of deleted or unknown IDs; do not rely on a custom URL scheme alone.

## 5. Admin/catalog workflow

### 5.1 Bulk catalog ingestion is missing (Medium-High (from project history), Observed workflow gap)

- **Repo/component:** `beer-passport-admin`.
- **Evidence:** The admin site has workflows for adding/updating/deleting beers and maintaining breweries, categories, styles, collections, and collection-beer relationships, but adding catalog records manually is high-friction; the existing admin interface is not an efficient bulk-ingestion workflow.
- **Impact:** Catalog maintenance is slow and error-prone; routine updates previously required manual SQL.
- **Remediation:** CSV/bulk import with column mapping, required-field validation, and preview before committing; duplicate detection for beverages and breweries with merge support; import report with accepted, rejected, duplicate, and warning counts; image provenance fields (source, license/permission, attribution, verification date, approval status); audit of the original catalog source license before reuse.

## 6. Monitoring, reliability, and release process

### 6.1 Sentry setup and sampling need review (Medium, Observed configuration; cost/coverage needs verification)

- **Repo/component:** `beer-passport-server`.
- **Evidence:** Sentry tracing/profiling initialized with sampling rates set to 1.0.
- **Impact:** May collect a high proportion of transactions/profiles depending on traffic and SDK config; errors may not reach Sentry until middleware ordering (1.5) is fixed.
- **Remediation:** Decide what to capture; use environment-specific sampling and a budget-conscious default; test a known exception in staging; never log tokens, passwords, private keys, or secrets.

### 6.2 API releases can break older installed mobile apps (High, Known product/release risk)

- **Repo/component:** `beer-passport-server`, `beer-passport`.
- **Evidence:** Mobile app is distributed separately from the backend; users can run older versions after an API deploy.
- **Impact:** Removing or changing fields/routes can break older clients.
- **Remediation:** Versioned API contract (e.g., `/api/v1`) with legacy endpoints during transition; additive response changes; contract tests for supported app versions; minimum-version/update-required mechanism only when necessary; deploy backend before depending on new client behavior; monitor with a rollback path.

### 6.3 Backups, restore drills, and spend alerts are not yet evidenced (High, Needs deployment/operations verification)

- **Repo/component:** deployment/operations (not established from code).
- **Evidence:** The source reviewed does not establish that production backups are configured, restoration has been tested, or cost alerts are in place.
- **Impact:** Unverified recoverability and cost control.
- **Remediation:** Confirm automated database backups and retention; run a restore test before migration and periodically after; add alerts for spend, API errors/latency, database availability, exhausted connections; document deployment, rollback, restore, and incident steps.

## Priority order (from the audit)

- **P0, before data migration or production cutover:** back up current data; eliminate `.env` from Docker build; confirm database persistence; correct auth error statuses and server-side authorization; test a restore.
- **P1, before public relaunch:** fix Express error middleware order; separate catalog seeding/import from startup; align Prisma versions; validate the PostgreSQL decision and migration; fix Universal Links and web fallback; add API compatibility tests.
- **P2, during relaunch build:** bulk catalog import/duplicate tools; paginated search; barcode representation review; friend-relationship integrity; notification event semantics; profile privacy tests; Sentry sampling review.
- **P3, after the foundation is stable:** additional product features and polish not needed to safely relaunch the core discovery/logging/collections/friends loop.
