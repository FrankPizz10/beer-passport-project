# 09: Old-Catalog Cleanup Strategy

Status: plan approved by Frank 2026-10-21. Implementation in `src/cleanup/`,
tests in `tests/test_cleanup.py`. Nothing in this plan edits the source
spreadsheets or the committed baseline snapshots.

## Why cleanup, and why this shape

The old catalog (5,894 beers, 1,431 breweries, exported from Frank's
spreadsheets, which are the source of truth) is the base of the relaunch.
The 2026-10-21 audit found it structurally sound: category and style are
100% populated, there is exactly one duplicate (name, brewery) group, and
no case for dumping it and starting over. What it has is a small set of
provable defects. This cleanup fixes only those, mechanically, with a
full audit trail, so the cleaned output can be trusted as the import
source for the relaunch database.

Two lessons from BeerPassport's history shape the design:

1. No manually maintained datasets. The cleanup is a script with named
   rules, not hand edits, so it can be re-run against a fresh spreadsheet
   export and produce the same result.
2. Nothing irreversible without review. The script has a report mode
   that changes nothing, and even apply mode writes new files only. The
   inputs are never modified.

## Inputs and outputs

- Inputs: the committed baseline snapshots in `data/`
  (`LiveBeers.partNN.csv`, `LiveBreweries.partNN.csv`), loaded through
  the existing `src/baseline.py` loader. These mirror the spreadsheets.
- Outputs (apply mode only), written to `cleanup/`:
  - `CleanedBeers.partNN.csv` and `CleanedBreweries.partNN.csv`, split
    into parts of about 90 KB following the repo convention, header row
    in part 01 only, so the existing baseline loader can read them back.
  - `CLEANUP_REPORT.md`, generated by the run (see below).
- Report mode writes only `CLEANUP_REPORT.md` and prints a summary. It
  writes no CSVs.

## The v1 rules

Every rule is provable from the data itself. Each affected row is logged
in the report with rule, entity, id, field, before, and after.

- **R1, empty breweries (drop).** A brewery whose id is referenced by
  zero beers is dropped from the cleaned brewery output. Audit count:
  92. A brewery with no beers carries no catalog content, and the drop
  is recoverable because the input is untouched and every drop is
  listed in the report.
- **R2, garbage UPCs (clear to 0).** The dataset's own null convention
  for UPC is `0` (5,888 of 5,894 beers have `0` or empty). The only
  other values present are 6 garbage entries: `2147483647` four times
  (the maximum 32-bit integer, a classic sentinel placeholder) and `7`
  twice (too short to be any real barcode format; UPC-A is 12 digits,
  EAN-13 is 13, UPC-E is 8). The rule clears a value to `0` when it is
  a known sentinel or an all-digit string shorter than 8 characters.
  A non-empty value in any other unexpected format is not changed; it
  is flagged in the report instead. Valid barcodes are never touched.
- **R3, discontinued markers (normalize).** 27 beer names contain the
  text `(discontinued)`. The marker is stripped from the name and
  recorded as data instead: the cleaned beer output gains a
  `discontinued` column (`1` when the marker was present, `0`
  otherwise). The beers themselves are kept. Discontinued status is
  information; burying it in a name string is the defect.
- **R4, duplicates (report only).** Groups of beers sharing the same
  normalized name and `brewery_id` are listed in the report and left
  unchanged. Audit found exactly 1 group. Merging needs a judgment
  about which row is right, so it is Frank's call, not the script's.

## Reconciliation

Apply mode ends with an accounting check, and the run fails if it does
not pass:

- Input beers = output beers (v1 never drops a beer).
- Input breweries = output breweries + dropped breweries, and every
  dropped brewery id appears in the change log.
- Every field change appears in the change log exactly once.

This makes silent data loss impossible: any row or value that differs
between input and output is either in the report or the run fails.

## Flow

1. Run in report mode. Review the report, including the full change
   list and the R4 duplicate flag.
2. Run in apply mode. Review the cleaned CSVs and the reconciliation
   result.
3. Separately, and only with Frank's explicit approval after review:
   decide whether the cleaned output becomes the database import
   source as-is, or whether the approved fixes are written back into
   the spreadsheets so the spreadsheets stay canonical. Recommendation:
   write back, keeping the pre-cleanup spreadsheet as a backup. A
   cleanup that never flows back into the source of truth evaporates
   the next time anyone uses the spreadsheets. No write-back tooling
   exists yet; it is a separate step with its own review.

## Explicitly out of scope for v1

- Deleting breweries or beers on suspected closure. The brewery
  liveness cross-check (2026-10-21) showed absence from Open Brewery
  DB proves nothing, especially for international breweries. Nothing
  is deleted on suspicion.
- Merging, renaming, or deduplicating beyond the R4 report flag.
- Filling in missing descriptions or ABVs, or matching images. That
  is enrichment, a separate step with its own plan.
- Editing the spreadsheets. See step 3 above.

## How to test

From `experiments/catalog-discovery/`:

    python -m unittest tests.test_cleanup -v
    python -m unittest discover -s tests -v
    python -m src.cleanup.cli --mode report
    python -m src.cleanup.cli --mode apply

Report mode first. Expected audit counts on the current baseline:
R1 drops 92 breweries, R2 clears 6 UPCs, R3 flags 27 beers, R4 lists
1 duplicate group. If a run disagrees with those counts, stop and
investigate before applying anything.

## Repo mechanics note

Outputs reuse the part-file convention because the push path caps a
single call at roughly 125 KB of payload. The cleaned catalog is about
the same size as the baseline (roughly 1.5 MB in parts), far below
GitHub's repository size guidance (under 1 GB ideal). Each snapshot is
written once as new files, which is the pattern that keeps repo
history from bloating.
