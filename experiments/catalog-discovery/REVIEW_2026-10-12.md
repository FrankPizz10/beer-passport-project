# Catalog discovery prototype: review 2026-10-12

Owner summary for the proof of concept on branch
`experiment/catalog-discovery-prototype` (PR #2).

## What changed in this review

- **Open Food Facts rate limit fixed.** The documented search limit is
  10 req/min/IP; the prototype's 3s delay allowed 20 req/min. Delay raised to
  6s. No workflow change, runs just pace themselves.
- **Relevance tiers added.** Candidates are now labeled `confirmed` (a search
  term matched the record), `uncertain` (kept for review, not a verified
  beverage), or `rejected` (excluded). The run summary reports
  `relevance_counts`. The 100 existing candidates predate the label and show
  as `unclassified`; their data is untouched.
- **Repeat tracking added.** The summary now counts `repeated_source_records`
  per run (records already seen, merged as updates instead of duplicates).
- **Identity semantics pinned down and tested.** New tests prove the same
  product under two search terms merges to one candidate, and document the
  known limitation that cross-*source* merging without record IDs is
  unsupported.
- **Docs updated.** README now records the source-policy findings (URLs and
  check date), the robots.txt vs API-docs analysis, license implications,
  and how to interpret results.

No state, outputs, or baseline snapshots were modified. Nothing was pushed.

## Current results (accumulated, from the shipped discovery state)

- Source records fetched: 100 Open Food Facts product records
  (all from the "hard seltzer" term; the "beer"/"cider" terms hit transient
  503s in that run). Open Brewery DB: 0 records (403, see below).
- Baseline matches: 1 confident match; 15 possible duplicates flagged for
  review (16 candidates carry a baseline ID).
- Candidates created: 100 total (57 new_candidate, 42 needs_review, 1 existing).
- Repeated source records merged: 0 in the shipped runs; a later
  verification run re-fetched 100 records and merged all as updates with zero
  duplicates created, confirming idempotent repeats.
- Likely same-product groups: 6 normalized (name, producer) collision groups
  covering 22 candidates, e.g. ("hard seltzer", "white claw") x5 and
  ("hard seltzer", no producer) x9. These are *not* auto-merged; they sit in
  the review queue as possible variants or data-entry duplicates.
- Unresolved duplicates: the 42 needs_review candidates (15 possible
  baseline duplicates, 27 with insufficient evidence, mostly generic names
  with no producer).

## What the experiment proves

- The pipeline works end to end: chunked baseline snapshots load (7,325
  rows verified), OFF search returns real packaged products, 3-stage
  matching runs, incremental state accumulates without inflating counts.
- OFF contains genuinely new packaged products versus the 2008-era
  baseline (57 of 100 unmatched, including recognizable current brands).
- The review burden is quantifiable and driven by identifiable causes:
  ~42% needs review, mostly generic product names and missing producers.
- One source failing does not stop the others; repeat runs are idempotent.

## What it does not prove

- **Producer enrichment value.** Open Brewery DB never returned data from the
  build environment, so whether it improves product matching is untested.
- **Cross-source product merging.** There is only one product source; the
  merge logic is unit-tested but has no live cross-source demonstration.
- **That "new" means new.** Unmatched against the baseline is not verified
  new; the baseline may simply lack the product, or matching may have missed.
- **Production suitability.** Licensing is unreviewed, the API rate limit
  caps collection speed (bulk download path unevaluated), and OFF itself
  gives no assurances of data accuracy.

## Source and licensing decisions still needed (yours, not mine)

1. **Open Food Facts licensing review.** Database is ODbL, contents DbCL,
   images CC BY-SA, with attribution and share-alike obligations that can
   bite on public reuse. Experimental access is not production approval.
2. **API usage form + contact email.** OFF docs ask for the usage form and a
   `AppName/Version (contact@email)` User-Agent. I did not file anything or
   put your email anywhere; say the word if you want that done.
3. **Open Brewery DB: retry or drop?** The 403 is Cloudflare bot protection,
   not a policy refusal (robots.txt allows `/`; reuse needs only credit).
   Run the prototype from your machine; if it works on a residential IP,
   the producer half of the experiment is back on.
4. **Collection strategy.** OFF docs point at bulk CSV/JSONL downloads
   beyond a few hundred products. API search is fine for evaluation, not
   for catalog-scale ingestion.

## Recommended next step

Run `python -m src.main --limit 100` from your machine. That single run
answers the biggest open question (does Open Brewery DB work off a
residential IP?) and exercises the new relevance and repeat counters. If
OBDB works, do a broader pass and judge producer coverage; if not, decide
whether the experiment continues with OFF alone via the bulk download.
